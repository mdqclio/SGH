## 1. Pieza A — autor en la fila (`migrations/resoluciones_sanciones_autor.sql`)

```sql
ALTER TABLE public.resoluciones ADD COLUMN IF NOT EXISTS modificado_por uuid REFERENCES public.usuarios(id),
                                ADD COLUMN IF NOT EXISTS modificado_at  timestamptz;
ALTER TABLE public.sanciones    ADD COLUMN IF NOT EXISTS modificado_por uuid REFERENCES public.usuarios(id),
                                ADD COLUMN IF NOT EXISTS modificado_at  timestamptz;

CREATE OR REPLACE FUNCTION public.fn_autor_fila()
 RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public'
AS $function$
DECLARE
  v_usuario uuid := (SELECT u.id FROM usuarios u WHERE u.auth_user_id = auth.uid());
BEGIN
  IF TG_OP = 'INSERT' THEN
    NEW.creado_por     := v_usuario;
    NEW.modificado_por := NULL;
    NEW.modificado_at  := NULL;
  ELSE
    NEW.creado_por     := OLD.creado_por;
    NEW.modificado_por := v_usuario;
    NEW.modificado_at  := now();
  END IF;
  RETURN NEW;
END
$function$;

CREATE TRIGGER trg_resoluciones_autor BEFORE INSERT OR UPDATE ON public.resoluciones FOR EACH ROW EXECUTE FUNCTION public.fn_autor_fila();
CREATE TRIGGER trg_sanciones_autor    BEFORE INSERT OR UPDATE ON public.sanciones    FOR EACH ROW EXECUTE FUNCTION public.fn_autor_fila();
COMMENT ON COLUMN public.resoluciones.creado_por IS 'Lo impone la base (trg_resoluciones_autor, ISSUE-097): usuarios.id de la sesión al crear; NULL sin sesión. Las N° 39 y 40 (2026-09-27) quedaron NULL: se cargaron antes del cambio y no hay registro de quién las cargó.';
COMMENT ON COLUMN public.sanciones.creado_por    IS 'Lo impone la base (trg_sanciones_autor, ISSUE-097): usuarios.id de la sesión al crear; NULL sin sesión.';
```

(Texto completo, con el encabezado, en el archivo.)

- **Usuario de la sesión** = `usuarios.auth_user_id = auth.uid()`, que tiene índice único. Sin sesión (service_role,
  MCP, migración), `auth.uid()` es NULL, así que `creado_por` y `modificado_por` quedan NULL. Nada falla por eso: las
  columnas son nullable.
- **Congelado siempre**: ninguna sesión cambia `creado_por`, ni por la API ni por una migración (probe A8). Corregirlo
  exigiría deshabilitar el trigger a propósito en una migración, y eso queda escrito.
- `modificado_*` se pone en **cada** UPDATE, aunque no cambie nada visible (p. ej. "Publicar" o "Notificar").
- `resolucion_entidades` no lleva autor propio: pertenece a su resolución y la cubre la auditoría (pieza B).
- **Rollback A** (`rollback_resoluciones_sanciones_autor.sql`): saca los triggers, la función y las dos columnas
  nuevas, **perdiendo lo que hayan registrado**, y quita los COMMENT. `creado_por` y sus valores no se tocan.

## 6. Qué costaría hacer inmutable una resolución notificada (para plantearle a Fede)

**Hoy**: una resolución pasa por `borrador → publicada → notificada` (botones de `resoluciones.html`). En cualquier
estado, staff del club puede editar **todo** (número, fecha, tipo, texto, reunión, estado, documento) y, desde la
pieza C, sólo super_admin puede borrar. Las N° 39 y 40 están `notificada`.

**La regla propuesta**: una vez `notificada`, la resolución no se edita ni se borra. Un error se corrige con **otra
resolución** que la rectifica o la anula.

| Qué hace falta | Detalle | Tamaño |
|---|---|---|
| Base: congelar | Trigger `BEFORE UPDATE OR DELETE` en `resoluciones`: si `OLD.estado = 'notificada'`, error. Mismo corte para `resolucion_entidades` de una resolución notificada. ¿Excepción para super_admin con motivo, o ninguna? | 1 migración chica + rollback |
| Base: el vínculo | Columna `rectifica_a uuid REFERENCES resoluciones(id)` (y quizá `tipo_rectificacion`: rectifica / anula) en la resolución **nueva**. El estado de la vieja se **deriva** ("rectificada por Res. N°…") sin tocarla. | la misma migración |
| Pantalla | Para `notificada`: ocultar Editar y Borrar y mostrar "Rectificar", que abre una resolución nueva precargada con `rectifica_a`. Mostrar la cadena ("rectificada por…" / "rectifica a…"). | `resoluciones.html`, ~1 pantalla |
| Sanciones | Hoy la sanción se vincula a la resolución sólo por texto (`sanciones.codigo_resolucion`, sin FK). Si la resolución es inmutable pero la sanción no, corregir una suspensión = resolución nueva + **editar** la sanción (queda auditado y con `modificado_por` desde la pieza A). Para la misma garantía en la sanción: `sanciones.resolucion_id` (FK) y la misma regla. | aparte; más grande |
| Datos de hoy | La 39 y la 40 quedarían congeladas al aplicar, sin autor. Un error en ellas ya sólo se corrige con otra resolución. | — |
| Probe | Editar o borrar una notificada → error (staff y super_admin, según la excepción que se elija); rectificar crea la nueva con el vínculo; mutantes. | como el de esta fase |

**Contras a poner sobre la mesa**:
- Un error de tipeo en el número o la fecha detectado después de notificar obliga a emitir otra resolución con otro
  número (`UNIQUE (club_id, numero)`).
- Hace falta decidir qué pasa si se notificó por error (¿volver a `publicada`? sería editar una notificada).
- Si hay excepción para super_admin, conviene que exija motivo y quede en la auditoría. Si no la hay, la única salida
  es una migración.

**A favor**: es la práctica de los actos administrativos (lo notificado no se reescribe; se rectifica con otro acto),
y con A+B ya queda quién y cuándo en cada paso.

Estimación: base + pantalla + probe de la parte "resoluciones" ≈ el tamaño de esta fase. La parte "sanciones con FK a
resolución" es un cambio de modelo aparte.
