# 1. LOS TRES CAMBIOS

## 1.a — El guard mira las LÍNEAS, no la cabecera

`loadLiquidaciones` ya trae `liquidacion_detalle(*)` embebido, así que el conteo sale sin una
consulta más:

```javascript
function comprometidasDe(l){
  return (l?.liquidacion_detalle || [])
    .filter(d => d.recibo_id != null || d.estado_linea === 'pagado').length;
}
```

**El `|| d.estado_linea === 'pagado'` es el grueso del agujero, no un detalle.** Medido contra
una liquidación real:

```
liquidacion con pagado-sin-recibo: 54317177-4de0-4e9c-ae59-20cc63cd9c9b
lineas totales                : 6
solo recibo_id (filtro viejo) : 0   <- lo que habria contado ayer
filtro completo (el nuevo)    : 6   <- lo que cuenta ahora
```

Esa liquidación era **enteramente borrable** con el criterio anterior.

## 1.b — Badge, no ausencia

```javascript
${l.estado===\x27pagada\x27 ? \x27\x27 : (comprometidasDe(l)
  ? `<span class="badge badge-pagada" title="No se puede eliminar: tiene líneas ya cobradas. Para revertir un cobro se usa Anular recibo, en el tab Pagos.">🔒 ${comprometidasDe(l)} cobrada(s)</span>`
  : `<button class="btn-sm btn-delete" onclick="eliminarLiq(\x27${l.id}\x27)">🗑️</button>`)}
```

Un botón que no está deja al operador buscándolo; un candado con el conteo dice qué pasa y
adónde ir. El `title` nombra la salida: **Anular recibo, en el tab Pagos**.

## 1.c — El re-chequeo contra la base

El render es una foto. Entre que se pintó la tarjeta y el click, alguien pudo emitir un recibo
desde el tab Pagos —que ahora es una solapa aparte, y por diseño no refresca ésta—. Así que
`eliminarLiq` vuelve a preguntar:

```javascript
const { data: comps, error: eChk } = await sb.from('liquidacion_detalle')
  .select('id,concepto,monto_neto,estado_linea,recibo_id')
  .eq('liquidacion_id', id)
  .or('recibo_id.not.is.null,estado_linea.eq.pagado');
if (eChk) { console.error(\x27[eliminarLiq/chequeo]\x27, eChk); toast(eChk.message,\x27error\x27); return; }
if (comps?.length) {
  const total = comps.reduce((s,d)=>s+(parseFloat(d.monto_neto)||0), 0);
  toast(`No se puede eliminar: tiene ${comps.length} línea(s) ya cobrada(s) por ${fmt(total)}. `
      + `Para revertir un cobro, anulá el recibo desde el tab Pagos.`, \x27error\x27, 9000);
  loadLiquidaciones();   // la tarjeta estaba vieja: repintar para que aparezca el candado
  return;
}
```

El `.or()` verificado contra la base antes de escribirlo:

```
2 comprometidas → [["pagado","con recibo"],["pagado","con recibo"]]
```

## 1.d — El error del primer `delete`, que había que arreglar igual

Antes:

```javascript
await sb.from('liquidacion_detalle').delete().eq('liquidacion_id', id);   // ← sin mirar el error
const { error } = await sb.from('liquidaciones').delete().eq('id', id);
if (error) { toast(error.message,'error'); return; }
toast('Liquidación eliminada');
```

Ahora:

```javascript
const { error: eDet } = await sb.from('liquidacion_detalle').delete().eq('liquidacion_id', id);
if (eDet) { console.error('[eliminarLiq/detalle]', eDet); toast(eDet.message,'error',9000); return; }
```

**No es cosmético.** Con el trigger de la opción 3 puesto, ese `delete` va a ser exactamente el
que falle — y sin este arreglo la función seguiría de largo y le diría al operador
"Liquidación eliminada" sobre un borrado que no ocurrió. El guard del servidor sin esto es
peor que nada: rechaza y miente.

## 2.a — `U4`: cómo se prueba un error que no puede pasar

Con `service_role` no hay forma de que el `delete` del detalle falle de verdad. Y lo que hay
que probar no es que falle: es **que la función se detenga cuando falla**. Se inyecta un cliente
que falla sólo en esa llamada:

```javascript
const sbFalla = {
  from(tabla){
    if (tabla !== 'liquidacion_detalle') return sb.from(tabla);
    const real = sb.from(tabla);
    return { select: (...a) => real.select(...a),
             delete: () => ({ eq: async () => ({ data:null, error:{ message:'permission denied for table liquidacion_detalle', code:'42501' } }) }) };
  },
  rpc: (...a) => sb.rpc(...a),
};
```

Tres asserts sobre eso, y el tercero es el que más importa:

```
 ✅ U4) si el borrado del detalle falla, la cabecera NO se borra (el error ya no se ignora)  → la liquidación sobrevivió
 ✅ U4b) y el error se le muestra al operador, no queda en silencio  → "permission denied for table liquidacion_detalle"
 ✅ U4c) y NO se avisa "Liquidación eliminada" sobre un borrado que no ocurrió  → ["permission denied for table liquidacion_detalle"]
```

`U4c` prueba que **no se dice "eliminada" sobre un borrado que no ocurrió** — el modo de falla
que el arreglo 1.d viene a cerrar.

## ISSUE-068 — nuevo, como pediste

Las policies de DELETE de `liquidaciones` y `liquidacion_detalle`, separadas del alcance.

Con una diferencia que conviene tener escrita antes de intentar repetir la receta de ISSUE-065:

> A diferencia de `recibos`, acá **sí hay borrado legítimo desde la aplicación**: el motor
> (`liquidaciones-engine.js:286` y `:367`) borra líneas no comprometidas y cabeceras vacías en
> cada recálculo, y `eliminarLiq` borra liquidaciones sin comprometer. **No se puede revocar sin
> más** — habría que mover esos borrados a un RPC `SECURITY DEFINER`, o restringir la policy a
> las líneas no comprometidas.
